# LOOM-177 gap report: what on-demand machines still lack end to end

**Epic:** LOOM-177 (Vikunja 1474, GitHub #359), "Target provider plugins: create dedicated targets and
workspaces on demand". **Read:** `origin/main` at `e623643`, `docs/design/target-providers.md` (the LOOM-178
design, approved 2026-10-09), `loomux/web` at `main`, and the open PRs #401–#406. Read-only: nothing was run
against TEST or prod for this report.

## The path, step by step

The goal: a person asks for a machine (web or chat), a plugin provisions it, a workspace lands on it, an agent
runs there isolated, and the machine is stopped, torn down, kept within quota and garbage-collected without
anyone tidying up by hand.

| Step | On `main` | Open PRs | Gap |
|---|---|---|---|
| Install and configure a plugin | API: `/api/v1/plugins` (install, config, enable/disable, upgrade, check, uninstall); bundled and sidecar sources; deep health and metrics | | No web page (G1); no declarative seed for GitOps deploys (G6); non-bundled plugins can't be verified, only "unsigned" (G5) |
| Create a machine | API: `POST /api/v1/targets` with `plugin: {id, size, persistent, egress}`, then `GET /targets/{id}` while it comes up | | **No web flow (G1); no way from chat (G2)** |
| The plugin provisions it | Kubernetes plugin (pod, PVC, Secret; TEST e2e passed 2026-10-20); Docker plugin (local e2e of both transports) | #406: a cold image pull is progress, not a failure; #402: canary pods deleted after their verdict | Docker on a real host (jet01) never run, needs the user (G7); Docker reports no pull progress (G8) |
| It becomes a target | Managed SSH, host key generated and pinned before contact, sshd on 2222; attach-info's `attach_commands` | #401: attach commands name the instance's tmux socket | |
| A workspace on it | The router provisions one when a chat asks for work on that machine; created machines are in its snapshot (`CreatedBy`, `Ephemeral`) | | No way to make one on a chosen machine outside chat (G3) |
| The agent runs isolated | A pod or container per target, PSA restricted; Kubernetes egress `none` behind deny-all NetworkPolicies and a per-node canary (LOOM-201, LOOM-208); vault `target_id` scope; persistent home for a one-time sign-in | #403: egress `none` re-checked on running machines | Docker offers internet only (decided 2026-10-10); no sandboxed runtime (later, design §13.14) |
| Lifecycle | `start`, `stop`, `recreate`; a dispatch to a stopped machine starts it first; `update_available` when the image changed; reconcile every 5 minutes and at startup | #405: the plugin tells the host at once (`targets.changed`) | A dispatch's wait doesn't allow for a pull (G9) |
| Teardown | `DELETE /targets/{id}` cascades (workspaces, tasks, target credentials, the machine, its key); uninstall with `targets=destroy\|keep` | | |
| Quotas | Per plugin instance: `max_environments` (create refused at the limit); the agents namespace's ResourceQuota on the cluster side; canary quota math documented | #402 keeps the canaries from lingering | |
| Garbage collection | Orphans (this instance's label, no row) destroyed after 24 h; a lost ephemeral machine's workspaces archived | | **A machine nobody uses runs indefinitely (G4)** |
| Deploy | TEST: the Kubernetes plugin as a sidecar (LOOM-178 Part B) | | Prod: not deployed (the user's call); pre-pull and the prod policy engine are deployment work (G11) |

## Gaps

Sizes: **S** a day or less, one PR; **M** a few days, one or two PRs; **L** a week or more, or several PRs.
command-center filed them on 2026-10-23 as the tickets in the last column.

| # | Gap | Size | Proposed ticket | Depends on | Filed as |
|---|---|---|---|---|---|
| G1 | **Web: no plugin UI.** `loomux/web` has the Machines page for registered hosts only: no Plugins page (catalog, install with the schema form, check problems, upgrade, uninstall), no "Create a machine" flow (plugin, size, keep data, egress, a progress strip from `GET /targets/{id}`), no created-machine card (badge, Stop/Start/Update/Delete, warnings, the `kubectl`/`docker` attach command). Design §6 (PR 6 of the plan). Until it lands, a person creates a machine only with `curl`. This is the largest gap on the user's path. | L | Web: Plugins page and the create-machine flow (target providers PR 6) | none (API on `main`) | LOOM-214 (#408) |
| G2 | **Chat can't create a machine.** No `provision_target` routing action; the router doesn't know machines can be created, so a request for one gets no useful answer (the design's interim "direct answer naming the page" isn't there either). | M (interim answer: S) | Router: create a machine from chat (`provision_target` behind a confirmation); interim: answer how to create one | G1 for the interim answer to name a page | LOOM-216 (#410) |
| G3 | **No workspace without chat.** `POST /api/v1/workspaces` doesn't exist (the v1 freeze lists it as addable), so neither the web nor a script can provision a workspace on a chosen machine. | M | API: `POST /workspaces` to provision a workspace on a chosen target | none | LOOM-215 (#409) |
| G4 | **Idle machines run indefinitely.** Nothing stops a created machine nobody uses: its pod or container holds its CPU, memory and the namespace's `pods` quota until someone presses Stop. A dispatch already starts a stopped machine, so stopping an idle persistent one is transparent to the next request. | S | Created machines stop when idle (opt-in), started again on the next dispatch | none: **implemented in #419** | LOOM-217 (#411) |
| G5 | **Non-bundled plugins can't be verified.** `plugins.Catalog.Verifier` exists but nothing implements or wires it, so a directory plugin is always `unsigned` (design §1.6 wants LOOM-118's Sigstore verifier, as for the web bundle). | M | Verify non-bundled plugins' build attestations (LOOM-118 verifier) | none | LOOM-218 (#412) |
| G6 | **No declarative plugin config.** Plugin instances are configured through the API only; theWyseKube's Flux deploys would want `LOOMUX_PLUGINS_SEED` (design §13.19's follow-up, applied once when the database has no such instance). | S–M | Seed plugin instances from `LOOMUX_PLUGINS_SEED` | none | LOOM-219 (#413) |
| G7 | **Docker plugin follow-ups.** The by-hand run on jet01 (needs the user's go); `port_range` for published SSH ports (decision 3 of #348). | S each | Docker plugin: `port_range`; Docker plugin: first run on jet01 | the user (jet01) | LOOM-220 (#414) |
| G8 | **Docker reports no pull progress.** After #406 the host waits out a pull a plugin reports; the Docker plugin pulls in the background without saying so. | S | Docker plugin: report image pulls as progress | #406 | LOOM-221 (#415) |
| G9 | **A dispatch's wait ignores pulls.** `EnsureRunning` waits 5 minutes for a machine coming up, whatever it is doing; a dispatch to a machine still pulling fails (retryably; the machine is unaffected). | S | Dispatch waits out an image pull on a machine coming up | #406 | LOOM-222 (#416) |
| G10 | **Policy drift isn't pushed.** Once #403 and #405 are in, #403's policy open/close transitions should send `targets.changed` like LOOM-208's node verdicts do in #405. | S | Kubernetes plugin: notify the host when the policies open or close | #403, #405 | LOOM-223 (#417) |

## Recommended order

1. **G4** (S, #419): the only GC gap on the path, and it frees cluster resources at once.
2. **G1** (L), the web flow: without it the feature is API-only. It needs no server change.
3. **G3** (M), then **G2**'s interim answer (S), then **G2** (M): chat and scripts reach the same machines.
4. **G6** and **G11** together, when prod is decided: a declarative config makes the prod deploy reviewable.
5. **G5**, **G7–G10** as they come; G8–G10 once their PRs merge.
