# LOOM-244: keeping `max_environments` across processes (design proposal)

**Ticket:** LOOM-244 (GitHub #457), "Provider plugins: max_environments can still be exceeded across two plugin
processes", a Medium finding of the 2026-10-21 audit for LOOM-201. **Read:** `origin/main` at `e2fa121`. This is
a proposal for review; no code changes with it.

## The race today

A machine is admitted in three places, each of them count-then-create:

| Where | Count | Create | Serialized |
|---|---|---|---|
| Host, `providers.Manager.plan` → `Create` (`providers/manager.go:440-448`, `:521`) | `ListEnvironmentsByPlugin` rows for the plugin instance | `CreateEnvironment`, after `CreateTarget` and two key generations | Not at all: two API calls or chat confirmations at once both count 4 of 5 and both insert |
| Kubernetes plugin, `createRecord` (`plugins/kubernetes/targets.go:122-141`) | this instance's record Secrets | the machine's record Secret | `createMu`, within one plugin process |
| Docker plugin, `runCreate` (`plugins/docker/targets.go:515-538`) | this instance's record volumes, plus this process's makings in flight | `build` (volume, container) | `p.mu` over the count only, within one plugin process |

Two plugin processes serve the same instance at once in two ways: the old and new instance during a plugin
upgrade (`plugins.Manager.Upgrade` starts the candidate beside the old one; a create in flight on the old one
runs on after the swap), and the old and new sidecar during a rollout (design §8 already counts canary pods
across "the configurations that can overlap" for the same reason).

Every machine is created through the host: the plugin only makes one when the host calls `targets.create`, and
the host inserts the environment row **before** that call (`Create` writes the rows and then starts
`runCreate`). It deletes a row only after the plugin's `targets.destroy` succeeded, or on purpose for a
machine it keeps (`detached`, uninstall with `targets=keep`). So the host's rows already work as a ledger of
the machines it asked for. The plugins' counts differ from it in one direction only: they also see machines
with no row: kept (detached) machines and orphans waiting out the 24-hour sweep.

## Options

### A. Reservation object (plugin side)

Each plugin claims a place in its own backend atomically before it creates, so its processes can't both take the
last one:

- **Kubernetes:** one ConfigMap per instance listing the reserved machine ids, updated with the API server's
  optimistic concurrency (`resourceVersion`; a `Conflict` re-reads and retries). Or claim names
  `loomux-slot-<instance>-<k>` for k < max, where `AlreadyExists` means taken.
- **Docker:** the engine has no compare-and-swap, so it has to be name uniqueness: a labelled volume
  `loomux-slot-<instance>-<k>`, where 409 means taken.

| For | Against |
|---|---|
| Cross-process for the plugin's own backend, and it sees kept machines and orphans too | Every plugin needs its own version, including third-party ones through the SDK. A protocol rule nobody enforces |
| Works even if something other than this host created machines under the instance's label | New objects to leak: a claim has to be released on destroy, swept when its machine is gone, and rebuilt when the claims and records drift. New RBAC (`configmaps` create/update) in the Role every operator deploys |
| | Doesn't fix the host's own race. The host would still insert a row and then get a quota refusal back. That's a machine in `error` and not a clean `409` before anything is made |

### B. Serialized admission (host side, in process)

A mutex per plugin instance in `providers.Manager`, held from the count in `plan` to `CreateEnvironment` in
`Create`.

| For | Against |
|---|---|
| A few lines; the refusal stays a clean `409` before any row, key or machine exists | Only within one server process. Two `loomuxd` processes on the same database (a rolling server update over a shared volume) both pass |
| No storage or protocol change | Holds the lock across `generateKey` and `generateHostKey`, which are quick but not free. Creates on one plugin queue behind each other |
| | Leaves the count and the insert as two statements. The next code path that inserts an environment has to remember the lock |

### C. Database-level admission (host side, atomic in the store)

The store admits the row and enforces the limit in one statement:

```sql
INSERT INTO environments (<columns>)
SELECT ?, ?, …
WHERE (SELECT COUNT(*) FROM environments WHERE plugin_id = ?) < ?
```

A new `Store.CreateEnvironmentWithin(ctx, env, max)` (or a `max` argument on `CreateEnvironment`; 0 means no
limit) returns `registry.ErrQuota` when no row was inserted. `providers.Create` maps that to `ErrQuota`
(`409`) and runs the cleanup it already has for a failed insert: it deletes the target row and releases the
key. `plan` keeps its count as an early refusal and for the `Machines`/`MaxMachines` it shows. The insert
decides.

A variant is a `BEFORE INSERT` trigger that compares against a stored limit. But the limit the host enforces
comes from the plugin's live `targets.describe`, not from anything stored. So the limit is better passed as
a parameter than kept in a trigger.

| For | Against |
|---|---|
| Atomic for every process sharing the database: SQLite holds its write lock through the statement, across connections and processes. A second server process on the same file is covered too, which B can't do | A `Store` interface change (one method), its conformance test in `registry/storetest`, and the SQLite implementation. A future store has to do the same atomically (Postgres: the same statement under `SERIALIZABLE`, or `SELECT … FOR UPDATE` on the plugin's row) |
| Every create goes through the host, and the row is written before the plugin is asked. If the host never has more than `max` rows, no plugin process is ever asked for more, however many processes serve the instance | It counts the host's rows, so it doesn't see kept machines or orphans (below) |
| No plugin, protocol, SDK or RBAC change; third-party plugins get it for free | |
| The refusal stays a clean `409` before any machine exists | |

## What C leaves, and why it's acceptable

With C, the plugin-side check matters only for machines that have a record but no row. Example: limit 5, three
rows and one kept machine. The host admits two creates (rows 4 and 5). Two plugin processes overlapping at that
moment (an upgrade or rollout) each count 4 records and both create, so there are 6 machines. That needs a kept
machine or an orphan, two plugin processes at once, and two creates inside that overlap. Within one process,
the existing `createMu` and in-flight counting still refuse the second create.

That's the remaining gap. It is narrower than LOOM-244's finding, and closing it takes A's machinery in every
plugin. I'd leave the plugins' per-process checks as they are, as a backstop that sees kept machines and
orphans, and say in the design (§4's resource-exhaustion row, where `max_environments` caps the count) that the limit is enforced by the host's
rows. The plugins' own count only narrows the case above. If the case ever matters, the follow-up is A's
claim names for the Kubernetes plugin alone, where the API server makes it cheap. Two plugin installs pointing
at one namespace, or two Loomux instances sharing an instance id, would also make it matter.

## Recommendation

**C**, as one PR:

1. `registry`: `ErrQuota`; `Store.CreateEnvironmentWithin(ctx, env, max int) error` (0: no limit), documented
   next to `CreateEnvironment`, with conformance cases in `registry/storetest`.
2. `registry/sqlite`: the conditional insert above. `RowsAffected() == 0` with no constraint error means
   `ErrQuota`.
3. `providers.Create`: insert with `plan.MaxMachines`. `ErrQuota` from the store goes through the existing
   failed-insert cleanup and comes back as `providers.ErrQuota`. `plan`'s count stays.
4. Design §4 and `plugins/kubernetes` / `plugins/docker` comments: the host's rows are the limit, and the
   plugin's count is a per-process backstop. The comment on `createRecord` ("the host counts too") becomes
   accurate.
5. A changelog fragment under `### Fixed`.

B could be added on top as a cheap in-process guard, but it adds nothing C doesn't already enforce, so I'd skip
it.

## Test plan

| Level | Test |
|---|---|
| Store conformance (`registry/storetest`) | Under the limit inserts. At the limit returns `ErrQuota` and inserts nothing. `max` 0 is unlimited. Rows in every status count (`creating`, `error`, `destroying`), as `ListEnvironmentsByPlugin` does today. Another plugin's rows don't count. The existing unique and foreign-key conflicts still come back as `ErrConflict` |
| SQLite, cross-process | Two `sqlite.Open` handles on one file stand in for two processes. Start with 4 rows and limit 5, then 16 goroutines split across the handles race `CreateEnvironmentWithin` behind a start barrier. Exactly one succeeds and 15 get `ErrQuota`, under `-race`, repeated (`-count=20`) to catch an ordering that slips |
| Host (`providers`) | The fake plugin offers `max_environments` 5, with 4 environments present. Two `Create` calls released together get exactly one machine and one `ErrQuota`. For the loser: no target row, no SSH key left behind, and the plugin got a single `targets.create`. Plus a regression test that `plan`'s early refusal and the `Plan` counts are unchanged |
| API | `POST /api/v1/targets` at the limit is still `409` with "limit" (`api/machines_test.go` already covers the mapping, which stays) |
| Plugins | Existing in-process tests stay (`createMu`, Docker's in-flight count). No new cross-process plugin test, since C doesn't change the plugins. If A's Kubernetes follow-up is ever done, its test is two `Plugin` values on one fake clientset where exactly one wins the last place |
