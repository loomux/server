Loomux is a self-hosted server that lets you talk to your coding agents
from a chat in the browser. The agents keep running in their normal
interactive mode in tmux on your own machines, so you can SSH in and
`tmux attach` to any of them while the chat goes on.

A small router model you choose reads each message, picks the workspace
and the agent, and starts the agent there (Claude Code or Codex) or
reuses one already running. The answer comes back into the conversation.
When an agent stops at a prompt Loomux recognises, such as a permission
request or a question, you get it as a card with Approve, Deny or Reply.

**Status: pre-alpha, single user.** One password protects everything,
and the API may still change before 1.0.

## Try it

Follow the [quickstart](https://github.com/loomux/server#quickstart): one
Linux machine with Docker runs the server and makes the agents'
machines with the bundled Docker plugin. The full install guide is
[`docs/deploy/install.md`](https://github.com/loomux/server/blob/main/docs/deploy/install.md).

Pin the image by its digest, the one this release lists:

```
ghcr.io/loomux/server:0.4.0@sha256:<digest>
```

Upgrading from 0.3.x or 0.2.0? Read "Before you upgrade" in the
[changelog](https://github.com/loomux/server/blob/main/CHANGELOG.md)
first: 18 migrations run, the first start re-seals the vault (an older
release can't read it afterwards, so keep the pre-migration snapshot),
the database moves to WAL mode, and chat routing now needs
`LOOMUX_MASTER_KEY`.

## What's new since 0.3.0

- **Machines on demand.** The bundled Kubernetes and Docker plugins make
  a machine (a pod or a container, with a persistent volume if you want
  one) per target, register it as an ordinary SSH target, and can stop
  it when it's idle (opt-in). On Kubernetes, a machine can have no
  network egress beyond cluster DNS, offered only while a canary on its
  node proves NetworkPolicy is enforced. You can ask for a machine from chat; nothing is created
  until you confirm the card.
- **Targets without hand-written SSH config.** Loomux generates its own
  SSH keys, scans and pins host keys, tests a target step by step, and
  moves an existing target over to its own key.
- **Router models set in the app**, through any OpenAI-compatible API or
  Anthropic's own, with keys set, tested and rotated from Settings.
- **Workspaces as git worktrees**, one checkout and branch each, and a
  workspace API that doesn't need a chat.
- **The API v1 freeze**: renames and removals, an error `code` on every
  error, and a contract test that makes any change to `/api/v1`'s routes
  and fields show in review, ahead of 1.0's additions-only promise.
- **The server side of the terminal client** (loomux/tui, not released
  yet): take a task over while you're attached to its pane, hand it
  back, link a terminal to your login.
- **Security hardening**, much of it from an audit: browser security
  headers, session lifetime and revocation, login throttling, ssh
  argument injection closed, vault ciphertexts bound to their rows,
  redaction fixes, and plugins from disk run only when a digest or a
  build attestation vouches for them (unless you turn that off for
  development).

Everything, with LOOM numbers, is in the
[changelog](https://github.com/loomux/server/blob/main/CHANGELOG.md).

The agent image is rebuilt only when `deploy/agent` changes. It hasn't
since 2026-10-11, so the plugins in 0.4.0 pin that build, which predates
`agent.yml` and was signed by `plugins.yml`. All four images are
linux/amd64 only.

## Verify an image

Every image carries a GitHub build-provenance attestation (SLSA v1). With
the [GitHub CLI](https://cli.github.com/):

```sh
gh attestation verify \
  oci://ghcr.io/loomux/server:0.4.0@sha256:<digest> \
  --repo loomux/server \
  --signer-workflow loomux/server/.github/workflows/image.yml \
  --deny-self-hosted-runners
```

- Use the same command for `plugin-kubernetes` and `plugin-docker`.
- For the agent image, the signer is
  `loomux/server/.github/workflows/plugins.yml`.
- Write `loomux/server` in lower case: `--signer-workflow` compares it
  exactly, and `Loomux/server` fails.
- To check that the server or a plugin image was built from this
  release's commit, add `--source-digest <the commit v0.4.0 tags>`. The
  agent image was built from an earlier commit (above).

## Known limitations

- Single user, with one password.
- Images are linux/amd64 only, and there are no released binaries: run
  the image, or build `cmd/loomuxd` from source.
- The web client can't take a task back from a person yet; that's API
  only (`POST /api/v1/tasks/{id}/release`). Watch-only holds aren't in
  yet.
- Docker machines have no egress isolation: they can reach the LAN.
- Redaction of known secrets from what Loomux relays and stores is best
  effort, not a guarantee.
- The API may still change before 1.0, which is the release that
  declares `/api/v1` stable.
