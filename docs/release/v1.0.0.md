# Loomux v1.0.0 — the release bar (LOOM-124)

**Status:** draft for the user's review (2026-10-05). Nothing here is
tagged or deployed as production until the user says so.

v1.0.0 is the first semver release of `loomux/server` (with the
`loomux/web` client it pins), redeployed cleanly on `loomux.jellyor.net`
as production. This page says what has to be true before that, what is
explicitly not in it, and how we check. Every gap names a LOOM ticket;
**(new)** marks ones command-center is asked to file.

## 1. Functional scope

In v1.0.0, all on `main` today unless noted:

| Area | What the user gets | Tickets |
|---|---|---|
| Chat | One password login; conversations; a router that answers directly, runs a shell command, or hands work to an agent | LOOM-31, 46, 64, 72 |
| Agents | Claude Code and Codex in native interactive mode in tmux, multi-turn in the same pane, completion hooks, launch profiles, version checks, install offers, substitution when an agent is missing | LOOM-71, 75, 78, 79, 87, 88, 91 |
| Workspaces | Provision (empty, git clone, existing dir) from templated recipes; reopen, archive, delete, repair | LOOM-60, 70, 90 |
| Targets | Local and SSH targets via a Tailscale sidecar; health probe; per-target policy (purpose, allowed agents, provision, shell, confirmation) | LOOM-59, 84, 86, 89 |
| Turns | Async dispatch jobs, progress card, cancel, restart recovery (re-attach), late output relayed, failed turns with retry | LOOM-80, 81, 82, 95, 99, 121 |
| Approvals | Agent prompts answered from a card (LOOM-97); router offers answered with Approve/Deny (LOOM-123: server#181, web#43) | LOOM-97, 123 |
| Takeover | Attach command shown in the UI; human takeover | LOOM-20, 100 |
| Notifications | ntfy on done, failed, needs you, with a link | LOOM-102 |
| Web | Installable PWA; shows its own version | LOOM-102, 118 |
| Context | Fresh agents get the earlier conversation, scoped to the target's purpose | server#174–176 |
| Ops | Metrics, health probes, backups, pre-migration snapshots | LOOM-92, 103, 105 |

**Not in v1.0.0:** mobile/iOS/Android clients (LOOM-1); a second user or
roles; storage backends other than SQLite; the companion daemon on
targets; in-place web updates in production (see §3).

## 2. Robustness (LOOM-73)

The 2026-10-02 failure-mode report filed LOOM-74…116. 29 shipped with
merged PRs. **These 11 are closed on GitHub but have no merged PR in
either repo**, and the code shows them not done (or only partly). Their
GitHub issues should be reopened, and Plane checked:

| Ticket | Item | State found | v1.0.0 |
|---|---|---|---|
| LOOM-115 | HTTP server hardening (ReadHeaderTimeout, …) | `http.Server` has no timeouts | **must** (small) |
| LOOM-113 | Keep vault secrets out of argv | vault env goes into the tmux launch command as `VAR='secret'`, visible in `ps` on the target | **must** |
| LOOM-108 | Redact secrets before relay; data-sharing policy | command output is redacted; agent pane output goes to the relay model unredacted | **must** |
| LOOM-85 | Classify SSH/target errors | health probe covers reachability; no typed classes in chat errors | should |
| LOOM-109 | Rate-limit / login / compaction detectors | login prompt detected (LOOM-97); no rate-limit or compaction | should |
| LOOM-107 | Router resilience (retry, circuit breaker) | escalation model exists; no corrective retry or breaker | should |
| LOOM-114 | Target onboarding, host-key pinning via API | host keys strict from the mounted known_hosts; no API onboarding | defer (manual onboarding documented) |
| LOOM-104 | Alert rules via Alertmanager | 6 rules in theWyseKube `51-prometheusrules.yaml` | verify, then close |
| LOOM-110 | Dispatch audit trail | logs only | defer |
| LOOM-111 | Bracketed-paste delivery | send-keys | defer |
| LOOM-112 | Relay context (user message, prior summary) | not found | defer |

**Must** items block the release; **should** items go in if they fit
before the release candidate; **defer** items are listed as known
limitations in the release notes.

## 3. Security and secrets

- **Auth.** One bcrypt password (`LOOMUX_AUTH_PASSWORD_HASH`), sliding
  sessions, login backoff. All API routes but login/version need a
  session. TLS ends at the ingress.
- **Secrets in production**, all in the SOPS-encrypted Secret, none in
  the image: master key, password hash, router API keys, ntfy token. A
  fresh production instance gets **new values for all of them**, not the
  test instance's (new secrets are the user's to create; gate).
- **`LOOMUX_WEB_RELEASES_TOKEN` is unset in production** (user decision
  2026-10-05). The web client changes only through reviewed image bumps;
  the dashboard shows "updates aren't set up". The in-place updater
  (LOOM-118) installs only what `loomux/server` main pins; its open trust
  question (attestations need a paid plan or a public `loomux/web`) is
  with the user and does not block v1.0.0.
- **Web bundle provenance.** The image build checks the bundle against
  `deploy/web-sha256`, pinned in this repo (#179).
- **sc1** is `purpose: work`; agent context never crosses purposes.
  Whether sc1 also gets `allow_provision: false` and
  `require_confirmation: true` is open with the user.
- **Must before release:** LOOM-113, LOOM-108, LOOM-115 (§2), and a
  dependency/vulnerability pass: `govulncheck ./...` clean and
  `npm audit --omit=dev` clean or justified **(new: LOOM-124a)**.

## 4. Upgrade and database migrations

- Goose migrations 00001…00018, forward-only in practice; each runs at
  startup after the pre-migration snapshot (LOOM-92). Down migrations
  exist but aren't a supported path: roll back by restoring the
  snapshot.
- **Production starts from an empty database** (proposed): the test
  instance's conversations and workspaces are test data. Targets are
  re-registered. **The user decides** fresh vs carried over.
- After v1.0.0, every migration must keep a v1.0.0 database working, and
  its PR must say how it was tested against a copy of a real one
  **(new: LOOM-124b, a migration test against a v1.0.0 snapshot in CI)**.

## 5. Backup and restore

LOOM-92 is done (nightly online backup, PBS snapshot, pre-migration
copies; runbook in `docs/deploy/backup-restore.md`). **Must:** a restore
drill on the test instance, following the runbook to the letter, before
the release candidate **(new: LOOM-124c)**.

## 6. Install and operations docs

There is `README.md` and `docs/deploy/{container,ssh,targets,backup-restore}.md`.
**Must (new: LOOM-124d):** one install guide for a fresh deployment:
- every env var and secret;
- the data volume;
- the Tailscale sidecar;
- registering a target;
- logging in.

Plus an operations page:
- upgrade (bump the image tag) and roll back (previous tag + DB snapshot);
- rotate the password and keys;
- read logs and metrics.

## 7. Versioning and changelog

Strict SemVer 2.0.0 (user decision 2026-10-05): **0.y.z** pre-releases
while the API and schema still change (first **v0.1.0**), then
**v1.0.0-rc.N** once this bar is met, then **v1.0.0**. Server and web
share one version. Both repos keep a `CHANGELOG.md` (Keep a Changelog).
The image is tagged with the version, and `/api/v1/version` reports it.
The scheme and the cutting procedure are in
`docs/release/versioning.md`; the pipeline is LOOM-129. Tags wait for the
user's confirmation of the scheme.

## 8. The release e2e (release candidate on the test instance)

Run in a browser against the RC image, from a fresh login. It covers
LOOM-56's scope plus everything since:

1. Login, new conversation, direct answer.
2. `run_command` on jet01: typed in backticks (runs at once) and
   proposed (card → Approve; card → Deny; a stale card after a newer
   offer runs nothing).
3. Provision with Claude on jet01; multi-turn in the same pane; a
   clarification answer carries its task (server#174).
4. Async progress, cancel, plain-language failure.
5. Restart mid-turn: agent turn re-attached and delivered; the open page
   updates without a reload (web#39).
6. ntfy: done, failed and needs-you (offer) notifications arrive and
   open the conversation.
7. Workspace archive/delete/repair; target policy edit.
8. PWA installs; dashboard shows the web version and "updates aren't
   set up".
9. Backup taken; restore drill result recorded (§5).

Pass = every step as described, evidence (screens, log lines) in the
handoff. Agent substitution is covered by router tests (it can't be
forced from chat).
