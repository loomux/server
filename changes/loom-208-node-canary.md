### Security

- An egress `none` machine on Kubernetes is reported running only while a canary pinned to its own node (`spec.nodeName`) has found NetworkPolicy enforced there within the last 10 minutes (LOOM-208). Before, the one canary ran on whichever node the scheduler picked, so a policy engine missing from or broken on another node left machines there unconfined and running. Until its node is checked, the machine is `starting`; the check starts when a get, list or health sees the pod on its node. Verdicts go by when each probe ran, by the kubelet's container times, and an escape whose times are missing always counts. A node where the canary gets out makes each `none` machine on it an error, naming the node and what was reached. It also withdraws `none` from describe and create, refuses a start of a `none` machine still on that node, and check reports it until a check finds the node enforced again; a retry that can't run leaves it so. A canary that can't run on the node is tried again a minute later; meanwhile an "enforced" from the last 10 minutes still stands. The plugin checks the nodes of its `none` machines again every 5 to 6 minutes on its own. A check that gets out turns the machines there into errors, and with no "enforced" for 10 minutes they are `starting`. The per-node verdicts live in the plugin process, so after a plugin restart `none` machines are `starting` until their nodes are checked again: seconds, or up to the canary's 3-minute timeout while its image is pulled. Canaries need room in the agents namespace's pod quota: up to one per node being checked plus the check's own, for each plugin configuration whose canaries are still live. A restart or a rollout starts a fresh set while the old one's may run for up to 4 minutes, so allow `max_environments` + 2 × (nodes + 1) pods, plus (nodes + 1) for each further restart within 4 minutes. With too little room the machines stay `starting`; they are never reported running unchecked.
