### Security

- An egress `none` machine on Kubernetes is reported running only once a canary pinned to its own node (`spec.nodeName`) has found NetworkPolicy enforced there within the last 10 minutes (LOOM-208). Before, the one canary ran on whichever node the scheduler picked, so a policy engine missing from or broken on another node left machines there unconfined and running. Until its node is checked, the machine is `starting`. A node where the canary gets out makes each `none` machine on it an error, naming the node and what was reached. It also withdraws `none` from describe and create, and check reports it until a check finds the node enforced again. A canary that can't run on the node keeps the machine `starting` and is tried again a minute later. A running machine's node is checked again every 5 to 10 minutes while the host asks about it, and a check that gets out turns the machine to an error. The per-node verdicts live in the plugin process, so after a plugin restart `none` machines are `starting` until their nodes are checked again. Each check needs room for one more pod in the agents namespace's quota.
