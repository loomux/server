### Security

- An egress `none` machine on Kubernetes is reported running only while a canary pinned to its own node (`spec.nodeName`) has found NetworkPolicy enforced there within the last 10 minutes (LOOM-208). Before, the one canary ran on whichever node the scheduler picked, so a policy engine missing from or broken on another node left machines there unconfined and running. Until its node is checked, the machine is `starting`. A node where the canary gets out makes each `none` machine on it an error, naming the node and what was reached. It also withdraws `none` from describe and create, and check reports it until a check finds the node enforced again; a retry that can't run leaves it so. A canary that can't run on the node is tried again a minute later; meanwhile an "enforced" from the last 10 minutes still stands. The plugin checks the nodes of its `none` machines again every 5 to 6 minutes on its own. A check that gets out turns the machines there into errors, and with no "enforced" for 10 minutes they are `starting`. The per-node verdicts live in the plugin process, so after a plugin restart `none` machines are `starting` until their nodes are checked again. Canaries need room in the agents namespace's pod quota: up to one per node being checked plus the check's own, so allow `max_environments` + nodes + 1 pods.
